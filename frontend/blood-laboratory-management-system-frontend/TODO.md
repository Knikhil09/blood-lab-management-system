# Delivery outcomes

## Login and dashboard

- [x] **Login and main dashboard:** The Login screen must have username or email and password fields, a password show/hide control, and a Login button; validate missing credentials, display a clear invalid-credentials message, and show loading feedback while authentication is in progress. After successful authentication, navigate to the dashboard. Support logout and session termination. Integrate with Auth Service through the API Gateway and store authentication tokens according to the application's agreed security design. The Main dashboard must provide three primary actions: Add Test, View Reports, and Update Values; display the logged-in user's identity and a logout action; keep navigation and page titles consistent across screens.

## Patient and Add Test workflow

- [x] **Patient selection and registration:** Provide New Patient and Existing Patient choices. For a new patient, the Patient ID/code is generated by the backend and the frontend must not independently generate a patient code; for an existing patient, show its ID/code. Patient name, age, and gender are required; validate age in an acceptable range and provide a gender dropdown. Mobile is optional or required according to final policy; if validating by the current backend rule, validate 10 digits. Registration date defaults to today's date and registration time defaults to the current time. Search existing patients by ID/code, name, or mobile number, show matches and allow selecting the correct patient, populate saved patient details automatically and let the user verify them. Search/filter the patient list by ID/code, name, mobile, and relevant date; provide a clear/reset action; show an informative empty state when no patient matches.

- [x] **Test selection, dynamic results, report preview, save and PDF:** Load available tests from Test Service and support search by test name or ID; allow multiple tests to be selected for one patient; show selected tests clearly and allow removal before saving; prevent duplicate selections of the same test; do not hardcode the full test catalogue in React. Render result fields dynamically from selected test parameter configuration. Display each configured parameter name, configured unit when applicable, applicable configured reference range, and optional configured interpretation. Accept numeric or qualitative results according to parameter type, including qualitative choices such as Positive/Negative. Validate required values and permitted formats; support several tests in one report; preserve entered values when switching between selected tests; clearly identify incomplete or invalid fields. Preview Report shows the formatted report before saving; Save Report persists the report and results through the backend; Download PDF generates or retrieves the PDF for the saved report. The report includes patient details, test names, parameter results, units, reference ranges, relevant dates, and configured laboratory layout. Prevent accidental duplicate submissions and show save progress; show success only after the backend confirms the save; display a clear error if saving or PDF retrieval fails.

## Reports workflow

- [x] **Patient reports, historical details and actions:** Display a searchable patient list with patient ID/code, patient name, age and gender, mobile, registration date, and an action to open the patient's reports. Search/filter by patient ID or code, name, mobile, and relevant date; provide clear/reset; display an informative empty state when no patient matches. Show all saved reports associated with the selected patient, including report ID, report date, test names, status if supported, and an action to open the report; sort by date, newest first by default. View shows saved patient details, test results, and reference ranges stored for that report. Edit allows permitted fields/results to be changed; validate and save through the backend. Print opens a print-friendly report view. Download downloads the report as a PDF. Clearly identify the patient and report being edited; do not show a saved confirmation until the backend confirms the update; avoid accidental modifications to the wrong patient's report. Changing a test's current reference range must not silently change the range shown on an already saved report; the backend should preserve the range used when the report was created, and the frontend should show that stored snapshot for historical reports.

## Update Values

- [x] **Test parameter and reference-range management:** Search tests by test ID or test name; after selecting a test, display its configured parameters. Support numeric and qualitative tests; not every parameter uses lower/upper limits. For each parameter, display its name and unit; support configured numeric lower and upper reference limits where applicable and configured choices for qualitative tests. When both numeric limits apply, the lower limit must not exceed the upper limit. Require an explicit Save action and show success/failure feedback. Restrict changes to authorized users, with authorization enforced by the backend.

## Common behavior and integration

- [ ] **Validation, request states, accessibility, privacy and API Gateway integration:** Mark required fields clearly and show errors beside relevant inputs; prevent invalid submissions; validate mobile numbers, age, dates, and result formats; preserve user input after request failures wherever practical. Show progress while data is retrieved or saved; show an informative no-results state. Handle 400 Bad Request with validation feedback, 401 Unauthorized with missing/invalid authentication handling, 403 Forbidden with an explanation that the user lacks permission, 404 Not Found by showing the requested record was not found, 409 Conflict with duplicate-code/conflict feedback, and 500-series errors with a safe server-error message and a retry where appropriate. Use consistent navigation, page titles, Back and Cancel actions; confirm before discarding a lengthy report form; keep tables searchable and readable; use consistent date/time formats; support desktop/tablet layouts; provide accessible labels, keyboard navigation, and visible focus indicators. Authenticate through Auth Service and send API requests through API Gateway. Do not expose passwords, tokens, or secrets in the UI or logs; enforce authorization on the backend (hiding a button is not authorization); avoid displaying unnecessary patient information; do not overwrite protected identifiers such as patient code during routine updates. Use a centralized API client and separate API modules for authentication, patients, tests, and reports. Keep base URLs in configuration instead of scattering hardcoded URLs across React components. Patient endpoints must match actual PatientController mappings; report and test calls depend on endpoints implemented by those services. The frontend must call the API Gateway (port 8081). The provided frontend-only demo mode must be clearly identified as demo/mock behavior and must not claim mock writes are persisted by a real backend; synthetic sample records are for demonstration only. Actual endpoint mappings, authentication semantics, and PDF contracts were not provided, so gateway endpoint mapping must remain centralized/configurable rather than being guessed.

**Remaining integration work:** Set `VITE_USE_MOCK_API=false` and map the centralized routes/payloads to the actual Gateway/Auth/Patient/Test/Report services, then confirm session, authorization, and PDF contracts. The supplied requirements specify gateway port 8081 but do not provide route mappings or API payload contracts, and no real Spring Boot gateway was attached to this frontend workspace. The demo adapter and frontend workflows are implemented and covered by `pnpm test:mock`.
